# 計画と進捗の管理

## 適用と発見

- 計画作成・更新、進捗管理・引き継ぎ、既存計画に沿った作業・再開で適用する。計画作成の依頼は実装の許可ではない。着手する内容が現在の依頼・許可範囲に含まれるか確認する。
- 適用先の AGENTS.md と既存計画を読む。AGENTS.md の保存先・命名規則を優先し、同じ作業の計画があれば新規作成せず正本を更新する。完了済みの保存先も検索する。
- 配置規約がなければ、進行中は `docs/plans/`、完了済みは `docs/plans/done/`、名前は対象作業を表す kebab-case の Markdown（例：`search-filter-improvement.md`）を使う。ルート直下の汎用的な `PLAN.md` を作らない。
- 適用先の AGENTS.md には保存先2つ、命名規則、このスキルを適用する導線だけを置く。共通手順の本文を AGENTS.md や各計画へ複製しない。AGENTS.md の変更も現在の依頼範囲で行う。
- 新規作成時は [plan-template.md](references/plan-template.md) を読む。既存計画の修正や状態判断に迷う場合は [plan-examples.md](references/plan-examples.md) を読む。

## 進捗の正本

タイトルの直後に「進捗チェックリスト」を置き、`- [ ]` と `- [x]` のみで未完了・完了を表す。状態表、状況要約、別チェックリスト、作業日誌に進捗を重複記録しない。手動更新する完了件数・進捗率も持たない。既存計画に重複があれば必要な証跡を正本または詳細へ統合してから除く。

各項目は個別に完了を検証できる粒度とし、固有ID・簡潔な作業名、依存先ID（なければ「なし」）、完了条件、証跡／阻害要因／再開メモを持たせる。進行中・保留の場合だけ同じ項目の作業名に状態を補足する。その他はチェックだけで判定する。

長い設計、調査根拠、検証結果は詳細へリンクし、項目名を見渡せる簡潔さを保つ。詳細は進捗の複製ではなく根拠や仕様を置く場所とし、チェックを増やさない。未決事項は解決するタスクIDに結び付け、判断に必要な情報を詳細へ置く。秘密値・認証情報は計画にも証跡にも記録しない。

## 更新と完了判定

- 着手、検証結果の確定、完了、阻害要因の判明、方針変更の直後に該当項目を更新する。
- 完了条件を満たし、変更ファイル・検証結果・調査根拠などの証跡を記録してからチェックする。検証結果は対象、実行内容、結果を特定できる形にし、長いログは詳細へリンクする。
- 実装済みでも必要な検証が未実行・失敗なら未完了のままにする。実行できなかった検証を成功扱いしない。
- 保留は理由・再開条件・具体的な次の一手を同じ項目に残す。
- 方針変更では仕様と関連項目を同時に更新する。完了済み項目でも再作業・再検証が必要ならチェックを外し、過去の証跡が新条件の達成を示すと誤解されないようにする。
- 最終回答・引き継ぎ前に実態とチェックリストを照合する。スキルの適用だけで更新漏れを完全には防げないため、AGENTS.md からの発見・適用導線とこの照合を組み合わせる。

## 別セッションでの再開

実ファイル、Git差分、検証結果を既存計画と照合し、古いチェックや記述を信用しない。必要ならチェックを外し、証跡・阻害要因・再開メモを修正する。

進行中の項目、解除条件を満たす保留項目、依存先が完了した未着手項目から、現在の許可範囲で再開対象を判断する。依存先が未完了の項目や、許可されていない実装には着手しない。引き継ぎに必要な次の一手は該当項目に残し、別の「次の作業」一覧を作らない。

## 完了後の保管と再開

全チェック項目、計画全体の完成条件、必要な検証を満たしたら完了日（`YYYY-MM-DD`）を記録し、完了済み保存先へ移動する。計画を書き終えただけでは移動しない。計画のみの依頼でも、対象作業が未実施なら進行中の保存先に残す。

移動先に同名ファイルがないことを確認し、衝突時は日付などで一意な名前にする。同名ファイルを上書きせず、元の場所に複製を残さない。AGENTS.md などからの参照と計画内の相対リンクを新しい位置に合わせて更新し、解決先を確認する。詳細の証跡が指す実体を変えない。

完了済み計画を再開する場合は、同じ正本を進行中の保存先へ戻す。今回の変更で影響する項目のチェックを外し、依存項目の再検証要否も確認する。完了日を取り除き、リンクを再調整する。新しい完了時に改めて完了日を記録する。
