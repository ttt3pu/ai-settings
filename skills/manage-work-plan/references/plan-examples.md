# 判断が変わる記入例

以下は冒頭のチェックリストに置く項目の抜粋。別の状態表や進捗要約として転記しない。

## 未着手・進行中・保留・完了

```markdown
- [ ] P1 絞り込み仕様の確定
  - 依存先：なし
  - 完了条件：空入力と複数条件の期待動作が決まる
  - 証跡／阻害要因／再開メモ：なし
- [ ] P2 絞り込みの実装（進行中）
  - 依存先：P1
  - 完了条件：合意仕様を実装し、対象の回帰テストが通る
  - 証跡／阻害要因／再開メモ：src/filter.ts を変更。次は空入力の回帰テストを実行する
- [ ] P3 外部データでの確認（保留）
  - 依存先：P2
  - 完了条件：検証用データで期待結果を確認する
  - 証跡／阻害要因／再開メモ：検証用データ未提供。提供後かつP2完了で再開し、匿名化済みデータを読み込んで結果を照合する
- [x] P4 ヘルプ文の修正
  - 依存先：なし
  - 完了条件：仕様に合う説明となり、リンク先が存在する
  - 証跡／阻害要因／再開メモ：docs/help.md を修正、説明とリンク先の実ファイルを確認済み
```

P1が未完了のままP2の進行中を別セッションで発見したら、P1の根拠と実ファイルを確認する。根拠がなければP2の着手状態をそのまま信頼せず、依存先の解決まで保留に直す。

## 実装済みだが検証失敗

```markdown
- [ ] P2 絞り込みの実装（進行中）
  - 依存先：P1
  - 完了条件：合意仕様を実装し、空入力の回帰テストが通る
  - 証跡／阻害要因／再開メモ：src/filter.ts 実装済み。空入力のテストで期待3件に対し0件、失敗。次は空入力分岐を修正して再実行する。詳細は[検証結果](#p2の検証)
```

環境不足で未実行の場合は、失敗結果の代わりに未実行の理由・環境が整う条件・実行する検証を記録し、保留にする。

## 仕様変更で完了チェックを外す

空入力の新仕様を決定事項へ反映すると同時に、以前完了していたP2を次のように更新する。影響する依存項目も見直す。

```markdown
- [ ] P2 絞り込みの実装
  - 依存先：P1
  - 完了条件：空入力では全件を返し、新仕様の回帰テストが通る
  - 証跡／阻害要因／再開メモ：旧仕様の検証は通過済みだが新条件は未検証。次は空入力分岐と期待値を修正し再検証する
```

## 計画だけを依頼された場合

「絞り込み改善の計画を作成して」という依頼では仕様と作業項目を記入し、実装タスクは未チェックのまま残す。対象範囲に「今回の依頼は計画作成のみ」と明記する。実装せず、対象作業が未完了なのでdoneへ移動しない。

## 完了後の移動とリンク更新・再開

`docs/plans/search-filter-improvement.md` の全項目・完成条件・検証を照合して完了した例：

- チェックリストの下に `完了日：2026-10-08` を記録する。
- 同名衝突がないことを確認し、`docs/plans/done/search-filter-improvement.md` へ移動する。
- ルートAGENTS.mdの個別リンクがあれば `docs/plans/search-filter-improvement.md` から `docs/plans/done/search-filter-improvement.md` に更新する。
- 計画内の `../design/search-filter.md` を `../../design/search-filter.md` に直して、同じ実ファイルに解決することを確認する。元の計画は残さない。

追加仕様を依頼されたら同じファイルを `docs/plans/` へ戻し、P2など影響する項目のチェックと完了日を外す。リンクを逆方向に調整し、新仕様・完了条件・次の一手を更新する。
