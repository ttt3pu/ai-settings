# Create Pull Request

このスキルは、GitHubでPull Request（PR）を作成するためのスキルです。
このスキルが呼び出された際には、Instructionsに従って、PRの作成を行ってください。

# Instructions

現在の依頼がPR作成を含むことを確認し、利用側の `AGENTS.md` と既存のPRテンプレートに従って作成します。既存テンプレートがある場合は下記の共通テンプレートより優先します。

PRは以下のルールで作成します。

- `gh api user --jq '.login'`で取得したユーザーをAssigneesに追加すること
- PRのベースブランチは確認したデフォルトブランチにすること。ユーザーが別のベースを指定した場合はその指示を優先すること
- 非公開情報や移植元の名前・URLなど、公開を許可されていない情報をタイトル・本文に記載しないこと
- 必要なcommit・pushはそれぞれの許可範囲と利用側の規約を確認して行うこと。PR作成後はURLを報告すること
- PRのタイトル、本文どちらも日本語で記載すること
- PRのタイトルは変更内容を簡潔に表すものにすること
- PRの本文には変更内容を詳細に説明し、必要に応じて関連するIssueや背景情報を含めること
- PR本文では、変更したファイル名の羅列ではなく、「何ができるようになったか」「何の責務を整理したか」「どの利用者体験や開発体験が変わるか」が伝わるように書くこと
- ファイル名やパスは、説明に不可欠な場合のみ最小限にとどめること
- 作業ログのような列挙ではなく、変更の意図・結果・影響が伝わる表現を優先すること

## PR本文テンプレート

PR本文は原則として以下の構成を使うこと。

```md
## 概要
- この変更の目的を1-2点で書く
- 背景や、何を進めやすくした変更かを書く

## 変更点
- ユーザーや開発者から見て何が変わったかを書く
- 画面、API、データ契約、設定、運用のような意味のある単位で整理する
- ファイル名の列挙で埋めない

## 確認
- 実施した確認コマンドを書く
- 必要なら手動確認内容を書く
```

## 本文作成の観点

変更点の要約では、以下を優先して含めること。

- 何のための変更か
- 何が新しく可能になったか
- 既存構成のどの責務が整理されたか
- 後続作業がどう進めやすくなったか
- 実施済みの検証

## 避けること

- 変更ファイル名の羅列
- 「Aを修正、Bを修正、Cを追加」のような作業ログ調の箇条書き
- 背景や目的のない実装項目の列挙
- 実装者にしか伝わらない略語や文脈に依存した説明

## Command Examples

### PR作成の基本コマンド

本文は一時ファイルに実際の改行を保持して保存し、`--body-file` で渡すこと。
`<default-branch>` と `<body-file>` は確認したベースブランチと本文ファイルのパスに置き換えること。

```bash
gh pr create --title "PRタイトル" --body-file <body-file> --base <default-branch> --assignee "$(gh api user --jq '.login')"
```

ラベルは利用側の規約やユーザー指定がある場合に、対象リポジトリに存在するものを付与すること。
